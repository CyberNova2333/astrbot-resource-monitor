# 监控配置与探针参考

## 配置来源（本仓库最重要的一张表）

配置分三层，每一层只放它该放的东西。**越靠下的东西越不该进版本库。**

| 层 | 放什么 | 存在哪 | 入库吗 |
|---|---|---|---|
| 插件源码 | 判据的**形状**（怎么算、怎么比、怎么报） | 本仓库 | ✔ |
| 本地配置 | **配置源**（探哪里）+ 通知会话 ID + 凭证 + 少量本地开关 | 部署机上的插件配置（AstrBot WebUI）或本地配置文件 | ✘ |
| 配置源 | 线路表、阈值、要探哪些热更文件 | 由上一层指定的地址，或干脆就在上一层 | ✘ |
| 线路本身 | 文件清单与内容判据（每块的 hash） | 每条线路上的清单，现取 | ✘ |

### 配置源是可插拔的

**监控不绑定任何一份特定配置的形状。** 某个客户端的配置文件只是「其中一种源」
——它停用、换形状、或者某个端根本不读它，都不该让整套监控报废，因为监控真正
要探的东西（线路还活着吗、字节对不对）一个字都没变。

两种源，二选一（`watch/sources.py`，加第三种只需在那里加一个类，判据层一行不用改）：

```
A. endpoint —— 给一个能拉到线路表的地址
   本地配置 entry_url ──▶ 一份 JSON：只要有 mirrors[]（每条带 base）就能用
                            settings / watch / client 有就多探两样，没有就少探两样

B. mirrors  —— 直接给线路表，**不依赖任何中心配置**
   本地配置 mirrors: ["线路甲=https://a.example.test/", …]
                            没有上游就没有上游单点
```

B 的代价是拿不到线上阈值，于是速率一类的判据保持**未判定**——而不是拿一个写死
的默认值凑数（那是铁律 2 禁止的）。两种源之下，块内容一律仍按线路上清单里的
MD5 逐块认：**源回答「探哪里」，永远不回答「算不算好」**。

三条不许破的规矩，都有守卫或钩子钉着：

1. **插件里不留第二份线路表 / 文件清单 / 阈值。** 抄一份就会漂移，而漂移的
   表现是「监控全绿但用户装不上」——恰恰是这套东西最该避免的失败形态。
2. **示例与文档里的地址一律用 `example.test`。** 它是 RFC 6761 保留域名，
   永远不会解析到真东西，所以不存在「示例被照抄后打到某个真实主机上」。
3. **凭证只走部署侧配置 / CI secret。** `tools/check-no-endpoints.py` 在
   pre-push 与 CI 两处各拦一次，因为进了公开历史就擦不掉。

样例配置见 [`config.example.json`](../config.example.json)（真配置请命名为
`config.json` 或走 AstrBot 插件配置，`.gitignore` 已挡）。

## 监控的判据（为什么不是通用探活）

这条链路上绝大多数真实故障的形态是「**HTTP 200，但用户装不上**」：回源缓存了
半截文件、某条线路不支持 `Range`、上游配置拉不到而客户端静默回退到内置默认值。
这些在「探活返回 200 就算绿」的监控下**全部是绿的**。

所以本插件的判据有三条底线（细节见 CLAUDE.md 铁律 2–4）：

- **内容按 hash 认，不按状态码认**——客户端本来就是这么认的；
- **线路表与判据从线上自发现**，不在插件里写第二份；
- 专挑用户不会报、只有外部监控看得见的**静默失败**下手。

## 探针与判据

| 探针 | 判据 | 挂了会怎样 |
|---|---|---|
| 线上配置可达性 | 200 + JSON + 至少一条线路 | 客户端静默回退到内置线路，**用户无感** |
| 线上配置合理性 | 有启用的线路；版本闸门形状合法且不回退；代理前缀以 `/` 结尾 | 配置写错会误伤全体用户 |
| 清单可达性 | 200 + JSON + 条目可用（坏条目会点名） | 新用户装不了，老用户热更也停 |
| 块内容校验 | `Range` 取一块，**MD5** 与清单逐块比对 | 能下完但装不上——这条链路最常见的真实故障 |
| Range 支持 | 必须 206；返回 200 = 服务器忽略了 Range | 分片下载退化成整包重下，表现是「网特别慢」 |
| 线路一致性 | 同一文件在各线路的清单必须一致（多数派判） | 某条线路落后，一部分人拿到旧版本 |
| 版本 json | 200 + `version`/`size`/`md5` 三者齐全 | 客户端拒绝更新，热更静默停摆 |
| 热更包整包核对 | 边下边算，size + 整包 MD5 | 包内容与声明不符，客户端下完拒收 |
| 线路速率 | 与**线上配置给的** `min_speed_kbps` 比 | 低于客户端判停滞的速度，用户不停换线 |
| 证书有效期 | < 14 天提醒，< 3 天升级 | 过期即整条线路不可用 |

块校验一发验三件事——可达、Range 支持、字节正确——顺带得到一次真实测速样本。
取块是**轮转**而不是随机：要能回答「哪些块还没验过」，这正是 `/线路 覆盖率`
凭什么说线上是好的。

> **块哈希是 MD5，不是 sha256。** 这不是我们选的：客户端认包用的就是每块一个
> 32 位十六进制 MD5，块大小由清单自己的 `chunk_size` 给（不是写死的 16 MiB）。
> 监控必须用**同一份判据**，否则会出现「监控说好、客户端说坏」。

### 热更相关探针要探什么，由被监控方声明

版本 json 的文件名不在清单里，插件里也不写死。线上配置可以带一个可选的
`watch` 段：

```jsonc
"watch": {
  "version_files": ["version_a.json", "version_b.json"],
  "packages": { "version_a.json": "a.zip" }     // 声明了才做整包核对
}
```

没声明就跳过这几个探针（记为「未判定」，不报警）——**不知道该探什么时保持
沉默，比拿一份猜的清单去报警好**。

## 配置源挂了怎么办（只有 endpoint 模式有这问题）

用 `mirrors` 模式时不存在这一节的问题：没有上游就没有上游单点。用 endpoint
模式时它是整条链的单点——一挂，监控既不知道有哪几条线路，也不知道按什么判。
但**「不知道」不等于「什么都别做」**：那恰恰是最需要信息的时刻。所以入口失败时
这一轮不会就此收工，而是把「坏到什么程度」查清楚再报：

| 线索 | 回答的问题 | 会不会告警 |
|---|---|---|
| 失败分两类：**拉不到** / **内容坏了** | 找托管方，还是回滚文档 | 都是 P0，但说清是哪种 |
| 备用出口（`entry_urls`，可选） | 是文档内容坏了，还是这个出口挂了 | ✘ 只作线索 |
| 上一次的好线路表（有保质期） | 线路是不是也一起挂了 | ✘ 标为未判定，永不告警 |
| 与上次好配置比对 | 这次改动是不是把自己打死了（线路表腰斩、阈值段消失） | ✔ |

于是那条 P0 长这样——**已经替人查掉了第一步**：

```
🔴 P0 · 线上配置可达性 失败
  影响：客户端拿不到线路表，会静默回退到内置线路；用户无感，只有监控看得见
  线上配置  拉不到：连接超时（30s 未完成）

  备用入口 backup.example.test：正常，2 条线路（2 启用）
  → 配置内容本身是好的，坏的是主入口那个出口
  用 13 分钟前的旧线路表顺带探了一下：2/2 条线路的清单还拿得到
  → 线路那边看着是好的，客户端此刻靠内置线路还能撑，但新配置下不去
```

两条边界不许越：**旧配置只用来探，不用来判绿**（拿旧数字当判据就是铁律 2 说的
漂移），而且**过期就不用**——一天前的线路表说明不了现在，过期的线索会把人带偏。
说不出来比说错强。

## 命令

| 命令 | 作用 |
|---|---|
| `/线路 状态` | 所有探针的红绿一览 + 覆盖率 |
| `/线路 测 <线路名>` | 立刻对某条线路跑一轮（含慢周期探针） |
| `/线路 配置` | 线上配置的关键字段：版本闸门、启用了哪几条线、阈值 |
| `/线路 静音 30m` | 维护窗口（默认限管理员） |
| `/线路 取消静音` | |
| `/线路 覆盖率` | 抽样块校验覆盖到了百分之几（7 天窗口） |

`/线路 静音` 不是可选项：没有它，自己调线路时会被自己的 bot 轰炸，两周后人就
把整个 bot 关掉了——那等于监控不存在。

## 它跑在一个共享环境里

这是个 **AstrBot 插件**：同一个 bot 上装着别人的插件，群里坐着几百个不认识的
人，而它拿到的数据来自**远端**（配置源、各条线路的服务器）。所以有三条边界是
按「对面不怀好意」写的，不是按「对面出错」写的：

| 边界 | 挡什么 | 在哪 |
|---|---|---|
| 命令闸门 | 一条 `/线路 测` 复读机 = 一台流量放大器。默认只在通知会话里响应、打流量的命令限管理员、重命令有冷却；命令触发的轮次**永不**下整包 | `watch/commands.py` |
| 出群净化 | 告警里大量字符串不是我们写的（线路名来自配置源、文件名来自清单、错误文本来自对面服务器）。带换行的线路名能在群里**伪造出另一条 P0**；`[CQ:at,qq=all]` 能让一条线路的名字替我们 @ 全体 | `watch/render.py` `safe()` |
| 目标地址 | 配置源是远端内容，它不该能把线路指到 `127.0.0.1` / 内网，让监控替它敲部署机自己的内网 | `watch/probes.py` `check_mirror_targets()` |

还有两条是「别让自己变成问题」：整包核对**必须有字节上限**（否则一条坏线路可以
一直往我们这边灌数据，内存不涨但带宽和时间无上限），以及**同一时刻只跑一轮**
（一把 `asyncio.Lock`：命令与后台循环并发跑会让流量翻倍、状态互相打架）。

## 明确不做的事

写清楚边界，免得越做越大最后没人维护：

- **不做可用率 SLA 统计。** 这是给几个人用的告警器，不是监控平台。
- **不碰上游服务。** 不由我们掌控的东西，监控它只会产生我们无法处置的告警。
- **不自动修复。** 不自动切线路、不自动改配置——监控与执行分开，一个会误判的
  东西不该有写权限。
- **不在插件里存业务状态。** 故障状态机是可丢的，丢了最多重报一次。
