# 一次故障怎样成为可确认的通知

线路返回 HTTP 200 时，文件仍可能只有半截，或来自错误版本。插件先用当前客户端依据判断内容，再处理故障去重和投递。这里跟踪一轮检查产生通知，直到 QQ 官方会话的管理员明确确认；不使用真实地址或会话作为示例。

难点是一次检查成功返回不代表内容正确，平台提交成功也不代表收到，必须保留待处理通知直到满足对应确认条件。

## Step 1: 从当前配置得到检查依据

插件从有效 WebUI 配置或部署侧文件取得入口与通知设置，再由来源适配读取当前线路、文件清单和阈值。框架入口使用包内相对导入，判据层不依赖 AstrBot。

入口配置是抑制链的根：取不到当前配置时先报告这个故障，下游信息只能辅助诊断。上次好配置可保留作线索，不能用旧阈值判绿。[一轮编排](../../watch/runner.py)中的 `run_cycle` 按这个顺序发现、检查、汇总结果。

## Step 2: 由内容结果推进告警状态

内容检查按当前清单和摘要判定；不确定结果不计为已验证内容。状态层累积失败窗口、去重、抑制上游引起的下游噪声，并在满足连续成功条件后产生恢复。静音暂缓投递，不能消耗尚未发送的首次通知。

[告警状态](../../watch/state.py)将判据结果变成通知；[监控回归](../../tests/test_monitor_regressions.py)检查旧配置不提升、未知块不累计已验证覆盖、目标改变退休旧故障等边界。快慢检查分别调度，手动命令禁用重型整包操作，避免一条聊天指令触发大下载。

## Step 3: 先保存待处理队列，再尝试发送

框架入口把消息加入 outbox。状态保存失败时先保留队列，不先发送并假装可恢复。发送每一个接收者之前，都会重新检查静音和故障是否仍有效；上一个接收者等待期间发生恢复，后续接收者就不应收到过期故障。

[投递循环](../../main.py)中的 `_flush_outbox` 按此顺序执行；[投递回归](../../tests/test_delivery.py)明确覆盖“第一个接收者发送中恢复/静音”后阻止续发。这条检查必须按接收者执行，不能只在整批开始时检查一次。

## Step 4: 区分向平台提交与人工确认

适配器通过会话 UMO 的平台实例 ID 查询元数据，不能把 UMO 首段直接当作平台类型。QQ 官方主动消息要求适配器声明相应能力；消息输出为纯文本，链接省略，提及降级。

| 通知状态 | 可观察行为 |
| --- | --- |
| 平台能力缺失或未就绪 | 留在队列供后续查询，不声称已发出 |
| 官方发送调用未抛错 | 该会话写入 `submitted`，保留待确认，不每轮重发 |
| 管理员执行 `/线路 通知` | 展示本会话最早一条，绑定查看者与具体通知，不清除 |
| 同一管理员执行 `/线路 确认` | 只确认本人在本会话刚查看的一条；保存失败回退 |
| 插件重启 | 队列恢复，需重新查询再确认 |

这些是[框架接线](../../main.py)中的 `_pending_notification`、`_confirm_notification` 行为。发送 API 的返回值不能证明真人收到消息；普通平台移除成功会话的行为与官方待确认流程不同。

## Step 5: 用离线替身检查边界

```sh
python -m unittest tests.test_plugin_loading tests.test_delivery tests.test_qq_official
```

[包加载测试](../../tests/test_plugin_loading.py)核对包内导入，[官方消息回归](../../tests/test_qq_official.py)核对自定义平台 ID、纯文本和人工确认。[投递测试](../../tests/test_delivery.py)核对恢复、静音和落盘失败。本轮未执行这些业务测试；真会话权限、平台额度与实际送达必须在部署侧另行验收。
