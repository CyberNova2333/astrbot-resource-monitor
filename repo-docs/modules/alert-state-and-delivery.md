# 告警抑制窗口、持久化队列与人工确认

分布式监控面临两重压力：网络瞬时抖动不能每次都艾特全群，否则两天后告警就会被屏蔽；同时，平台发送调用返回正常也不等于值班管理员真正看到了告警。插件把判定结果收口到多轮窗口状态机和持久化投递队列，并在 QQ 官方适配器上把「已提交」与「人工确认」拆成两步。

在[完整运行主流程](../walkthroughs/one-real-run.md)中，探针汇总之后的所有告警收敛、落盘和群内交互均由这一层接管。

## 状态机窗口、抑制树与升级去重

[state.py](../../watch/state.py) 中的 `AlertState` 为每个 `(探针, 目标)` 维护独立的滑动窗口条目 `Entry`，用以下机制控制告警噪音：

- **M-of-N 窗口触发与连续恢复**：默认配置要求连续 3 轮中有 2 轮失败（`fire_after_failures = 2`、`fire_window = 3`）才从 `GREEN` 转入 `FIRING` 并产生 `fire` 通知；恢复也要求连续成功 2 轮（`recover_after_successes = 2`）才产生 `recover` 通知。`unknown=True` 结果按「不计失败」处理但不会在故障期间清空已触发状态或误报恢复。
- **两级抑制键（`suppress_key`）**：所有检查条目可携带上游键。当入口 `KEY_ENTRY`（即 `配置源可达性`）处于 `FIRING` 时，下游的配置合理性、清单可达性与线路一致性结果在状态机中仍各自记账，但禁止发出独立告警；当单条线路的清单键 `manifest_key(mirror)` 处于 `FIRING` 时，同线路的块内容、`Range`、速率、版本 json 与整包核对告警同样会被抑制。需注意 `证书有效期`（TLS）直接按线路域名和端口判定，不挂在配置抑制链下。
- **去重、重发间隔、升级与自动清理**：首次触发之后，同一问题每隔 `remind_every_hours`（默认 `6.0` 小时）才允许发出一次 `remind`；但如果级别从低级别升级到更高级别（例如 `P2` 证书提醒降到 3 天以内升为 `P0`），则打破冷却间隔立刻升级告警。完全恢复且窗口清零、无挂起恢复事件的干净条目由 `_evict_clean` 回收；已被配置移除的旧目标则由 `retire_removed` 显式清理。
- **全线路故障升级（全绿或全红聚合）**：[runner.py](../../watch/runner.py) 统计仍在故障中的不同启用线路数（同一线路上的多个坏块会按线路去重，不会把单条坏线路算成多条）；当全部启用线路都受阻时，主动聚合并升级告警级别。

## 静音规则与状态持久化

运维调线时可执行 `/线路 静音 <时长>` 挂起通知投递，底层直接与 `AlertState` 和持久化文件交互（参见 [store.py](../../watch/store.py)）：

1. **静音不消耗资格**：如果在静音期间某条故障刚刚攒够失败窗口变成 `FIRING`，它暂不发 `fire` 也不把 `has_notified` 置为真；只要静音结束后故障仍在，就会立刻补发首次通知。若一条**已经发过通知**的故障在静音期间彻底恢复，系统会记录 `pending_recovery_since` 与持续时长，等解除静音后的首次巡检通过 `flush_pending_recoveries` 补发恢复报告。
2. **先落盘后发送**：`AlertState`、配置快照年龄、`Rotation` 覆盖游标和待投递 `outbox` 一并写入 `<state_dir>/watch-state.json`（参见 [main.py](../../main.py) 的 `_persist` 与 `_restore`）。入队后如果写入磁盘失败，主循环会保留队列并在下一轮重试保存，而不先发消息却把状态丢在内存里。

## 逐接收者复核与 QQ 官方人工确认

发送通知时，配置往往填写了多个接收会话，其中既可能有普通群聊，也可能有存在频率或额度限制的 QQ 官方适配器（`QQ_OFFICIAL_PLATFORMS = {"qq_official", "qq_official_webhook"}`）。投递逻辑见 [main.py](../../main.py) 中的 `_flush_outbox`：

```text
准备发送队列 ──▶ 保存磁盘成功 ──▶ 遍历每个待发接收者：
                                   ├─ 触发 _discard_stale？(已静音或故障已恢复) ──▶ 丢弃余下过期任务
                                   ├─ 普通适配器：调用发送成功 ──▶ 从本条 targets 移除
                                   └─ QQ 官方适配器：调用未抛错 ──▶ 标为 submitted 留队等待确认
```

- **逐接收者前二次复核（`_discard_stale`）**：在向第 2 个或第 N 个会话发送前，重新核对 `AlertState` 是否被管理员静音、或者故障已在一轮新巡检中恢复，防止因第 1 个接收者平台卡顿而在恢复后继续向后续群组发过期故障。
- **QQ 官方待确认状态流转**：对于 `qq_official` 与 `qq_official_webhook`，插件通过解析会话 UMO 对应的平台实例元数据（而非硬拆 UMO 字符串前缀）识别官方平台并退化为纯文本通知（省略链接、`@全体` 改为文本说明）。主动发送调用无异常只把该会话记录标记为 `submitted`、阻止每轮自动轰炸，**不移除队列条目**。后续必须由**管理员**在对应会话里：
  1. 发送 `/线路 通知`（`_pending_notification`）查看本会话最早一条待确认消息（此时只展示并绑定当前查看者、当前会话与具体通知 ID，不清除条目）；
  2. 同一管理员再发送 `/线路 确认`（`_confirm_notification`，无论 `privileged_admin_only` 配置如何均强制校验管理员权限），且持久化成功后，才把该条从待确认队列真正移除。插件重启会清空「已查看展示绑定」，管理员需重新执行一次 `/线路 通知` 再确认。

## 代表性案例

- **正常与 QQ 官方确认流程**：某镜像在连续两轮快巡检出现「Range 支持」失败，第 3 轮窗口记为 `[True, True]` 触发一条 `fire`（`P1`）并进入 `outbox` 写入 `watch-state.json`。`_flush_outbox` 向配置的两个目标依次投递：第一个普通群接收成功后移出队列；第二个目标为 `qq_official` 平台，主动发送无异常后把目标状态更新为 `submitted`。随后插件重启，`outbox` 从磁盘恢复，管理员在该 QQ 会话发 `/线路 通知` 看到该条详情，再发 `/线路 确认` 将其正式移出待处理列表。
- **边界与并发取消案例**：在另一个多会话场景中，向第 1 个群发送耗时较长，等待期间后台完成新一轮巡检并让原故障连续两次成功恢复了 `GREEN`（或管理员触发了静音）。轮到第 2 个会话准备发送前，`_discard_stale` 检测到原故障不再有效，立刻丢弃这条过期的 `fire` 消息，不再向第 2 个会话发送错误警报。
